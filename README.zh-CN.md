# HotkeyHound 快捷键冲突排查器

[English](README.md) · **简体中文**

# 作者的话：这个软件是做什么的

**查清楚是谁偷走了你的快捷键——并且拿出证据。**

HotkeyHound 是一个 Windows 全局快捷键冲突排查工具。它回答 Windows 自己不肯回答的三个问题：
**哪些组合已经被占用**、**是谁占用的**、以及**为什么你按下去毫无反应**。

*与 Kimi Code 共同开发。*

**落地页：** <https://conste11ation117.github.io/HotkeyHound/>

![HotkeyHound 七个页面一览](docs/demo.gif)

*七个页面走一遍：占用扫描 → 按键归属 → 钩子检测 → 按键监视 → 配置真相表 → 钩子嫌疑 → 报告。*

## 跟其它工具比

这一行当里目前有四个还活着的工具，回答的是不同的问题。下面这张表**刻意写成诚实的**——别人某处更强，就写出来。

| | HotkeyScan | Hotkey Screener | Hotkey Detective | **HotkeyHound** |
|---|---|---|---|---|
| 列出已被占用的组合 | 761 | 列出已注册的 | — | **1650** |
| 已注册热键的归属 | 靠"屏幕上发生了什么"推断 | 全局钩子 + 模拟按键 | 全局钩子，你手按 | **全局钩子，你手按——或可选的批量自动按** |
| 被**键盘钩子**吞掉的键 | 只有在按下产生可见变化时才能发现 | 官方承认看不到 | 官方承认看不到 | **专门的检测器 + 配置知识库，带证据等级** |
| 解释"为什么被占" | 读 PowerToys / ShareX / OBS / AHK 配置 | — | — | **读六类软件，并把用到的配置文件路径印出来** |
| 按键监视（卡住的修饰键、重映射、过滤驱动） | 有 | — | — | **有（1.2.0）** |
| 32 位进程 | 仅 64 位 | **32 + 64** | 提供 x86/x64 两个版本 | **x64 + x86（1.3.0 起）** |
| 能拿给别人看的报告 | — | — | — | **自包含 HTML，中英双语** |
| 许可 | MIT | 闭源 | GPL-3.0 | MIT |

关于 32 位：Windows 只允许钩子注入到与安装它的进程**同位数**的进程，所以 HotkeyHound 会额外拉起一个很小的
32 位伴随进程来装 32 位钩子；两边把结果报进同一张表，每行都会标注位数。

实际意味着：**HotkeyScan 是最接近的同侪**——我们正是因为它的按键监视才补上这一块，1.2.0 起已经对齐，
**Hotkey Screener 对已注册热键的归属最直接**，而 **HotkeyHound 是把"按了没反应"的三种原因分开**的
那一个——被注册占用、在到达系统之前被钩子吞掉、或者它根本不是全局快捷键——并且**每条结论都给出证据**，
而不是直接下断言。

还有两条这个领域里谁都无法越过的边界：**钩子型快捷键和应用内快捷键列不出来**，因为 Windows 不把它们
放进任何一张表里。宣称能做到的工具都是在猜；这个工具会把「实测到」「从配置读到」「官方默认」三种
证据分开标注。

更老的选项也有：NirSoft 的 HotKeysList（只列注册项、不给归属，且只列到 Windows 8）、以及 PCHunter /
OpenArk 这类内核级反 rootkit 工具——它们能读 win32k 的热键表，但要加载未签名驱动，在现在开启
Secure Boot / HVCI 的 Windows 上会被拦，而且**依然看不到钩子**。

## 它要解决的问题

一台装了若干软件的机器——PowerToys、输入法、两三个聊天软件、厂商控制中心、显卡覆盖层——
会有几十个全局快捷键。按下去，有时毫无反应，有时触发了别的东西。Windows 不给你看这份清单，
也不告诉你是谁注册的。

现成的工具（例如知名的 Hotkey Detective）要求你手动按下那个键、然后给你一个进程名——但
**它不能告诉你哪些组合已经被占用**，而且它对**用键盘钩子实现的热键**完全看不见（这类热键不走
`RegisterHotKey`），而这恰恰是最会悄悄吞键的那一类。

## 四个引擎

| 引擎 | 作用 | 是否装钩子 | 是否需要管理员 |
|---|---|---|---|
| **A 占用扫描** | 用 `RegisterHotKey` 逐个试探全部「修饰键 × 按键」组合（约 1650 个），报出哪些已被占用。成功的注册会立刻注销，所以扫描本身没有副作用。 | 否 | 否 |
| **B 按键归属** | 安装全局消息钩子；当热键持有者收到命令时，注入的 DLL 把**是哪个进程收到的**报回来。 | **是** | 建议 |
| **C 钩子窃取检测** | 安装低层键盘钩子，判断你按的键是**根本没到达系统**（被更上层的钩子吞掉），还是到达了却在持有者看到之前被截胡。 | **是** | 建议 |
| **D 配置聚合** | 解析以明文保存热键设置的软件（PowerToys、Everything、OBS、NVIDIA ShadowPlay 注册表、壁纸引擎、MSI Afterburner），与实测结果做 diff。 | 否 | 否 |

引擎 A + D 会产出一张**真相表**，共四类：
- 有声明且实测被占用（配置里确实有，系统里也确实有人拿着）
- 有声明但没注册成功（软件没运行，或它用的是钩子——报告会写明）
- 被占用但无人认领（配置读不出来的：输入法、聊天软件、驱动工具）
- 空闲（可以直接拿来用——报告会给出具体候选键位）

在这些之上还有一层**钩子嫌疑知识库**。对于用键盘钩子实现快捷键的软件——PowerToys 键盘管理器、
输入法、QQ/微信、AutoHotkey 脚本、厂商控制中心、投屏工具——任何系统表都不会列出它们的键位。
HotkeyHound 在能读的时候读它们的配置、检查软件是否在运行，然后给出带**明确证据等级**的「嫌疑」结论
（实测到 / 从配置读到 / 官方默认 / 仅供参考），并附上它读取的配置文件路径。**绝不把猜测写成事实。**


## 快速上手

1. 从 [Releases](../../releases) 下载 `HotkeyHound.exe` 直接运行：免安装，也**不需要装 .NET**
   （Windows 10/11 自带 .NET Framework 4.8）。
2. **扫描总览 → 开始扫描**。看真相表，然后导出 HTML 报告。
3. 某个键行为不对，用**按键归属**：点「开始监听」，按下那个键，看是哪个进程收到的。
   以管理员身份运行才能看到提权进程（例如 PowerToys）。
4. 按下去完全没有痕迹，用**钩子检测**：它会告诉你这个键是不是在到达系统之前就被吞了。

### 命令行

```
HotkeyHound.exe                                   # 图形界面
HotkeyHound.exe --scan --report out.html          # 引擎 A + D，生成 HTML 报告
HotkeyHound.exe --listen --seconds 60             # 控制台归属监听（引擎 B）
HotkeyHound.exe --lang en --scan --report en.html # 英文输出
HotkeyHound.exe --elevate --listen                # 提权重启后再监听
HotkeyHound.exe --selftest                        # 自测（会装钩子，见下）
HotkeyHound.exe --monitor --seconds 10            # 按键监视：raw / 钩子 / 窗口三层
HotkeyHound.exe --selftest --no-hooks             # 不碰钩子的自测
HotkeyHound.exe --attribute-all --dry-run         # 规划批量归属，一个键都不按
HotkeyHound.exe --attribute-all --yes             # 逐个按下已占用热键，记录归属
```

## 安全模型

这个工具会触碰输入处理，所以它的行为被刻意收得很窄：

- **引擎 A / D 从不安装任何东西。** 注册热键后在同一瞬间注销；只读配置文件，
  **绝不修改配置或注册表**。
- **引擎 B / C 只在用户显式要求时才装钩子。** 界面按钮上直接写着「（安装钩子）」，
  程序加载时什么都不装。
- **钩子绝不吞键。** 钩子过程只观察、一律放行（`CallNextHookEx`），不改键、不拦键、不延迟。
- **绝不结束、暂停或修改任何其它进程。** 「对照排除」只记录观察结果，请你**自己**退出可疑软件。

### 关于注入的 DLL，以及一段必须公开的事故

引擎 B 的机制是安装全局 `WH_GETMESSAGE` 钩子，这意味着 Windows 会把一个原生 DLL
**加载进你当前会话里的每一个进程**。开发过程中，早期版本把钩子过程写成了 **.NET 托管委托**——
那个地址只在我们自己进程里有效，注入到别的进程后就是野指针，后果是**所有 GUI 进程在同一秒集体
崩溃**（异常码 `0xc0000409`，故障模块 `unknown`），也就是全机崩。

修复方式（用 `GetProcAddress` 取原生导出地址来装钩子）以及之后的加固——`DllMain` 里什么都不做、
把临界区换成一次性初始化、钩子热路径零分配——**已经在真机上验证**：反复装卸钩子、**崩溃事件 0 次**，
并端到端抓到过一次真实归属（`Win+R → explorer.exe`）。这段事故写进了 CHANGELOG 而不是被悄悄抹掉，
因为使用钩子类工具的人有权知道它的历史。

一次钩子会话结束后，被注入的进程里仍会留着一份 DLL，直到这些进程退出；**重启一次即彻底清除**。
界面里也会提示这一点。

## 已知限制

- **要处理提权进程，必须以管理员身份运行 HotkeyHound**，否则它们的热键查不到归属
  （界面会提示，并提供一键提权重启）。
- **32 位进程的归属看不到**：注入的 DLL 是 x64。引擎 A / D 不受影响。
- **钩子型热键对占用扫描不可见**（它们不调用 `RegisterHotKey`）——这正是引擎 B / C 存在的理由，
  报告里始终会印这句提醒。
- 探测是**会话级**的：别的登录会话注册的热键看不到。
- 验证环境为 Windows 11 26100 与 Windows 10 19045；其它版本未测试。

## 从源码构建

构建刻意做到零依赖：开发机上**没有 .NET SDK**，所以工程直接用 Visual Studio 自带的工具链编译。

```
powershell -ExecutionPolicy Bypass -File build.ps1
```

`build.ps1` 先用 MSVC 编译原生 hook DLL（`cl /LD /MT`），再用 Visual Studio 自带的 Roslyn
`csc.exe` 编译 C#（`.NET Framework 4.8`、`-langversion:7.3`、`-nostdlib+` 显式引用运行时程序集），
最后把 DLL 作为资源内嵌。产物是单文件 `dist\HotkeyHound.exe`。不联网、不用 NuGet。

目录结构：

```
src\Program.cs            入口、命令行解析
src\Core\                 引擎、模型、报告生成、设置
src\Core\Adapters\        各软件的配置读取（引擎 D）
src\Ui\                   WinForms 各页面
src\Hook\HookDll.cpp      原生 hook DLL（引擎 B）
tests\SelfTest.cs         T1–T7，由 --selftest 驱动
docs\                     帮助文档（中/英）
```
