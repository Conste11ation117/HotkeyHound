# HotkeyHound 快捷键冲突排查器

**查清楚是谁偷走了你的快捷键——并且拿出证据。**

一个 Windows 工具，回答 Windows 自己不肯回答的三个问题：

1. **哪些组合已经被占用了？** —— 逐个试探全部约 1650 个「修饰键 × 按键」组合，列出被占用的。
2. **是谁占用的？** —— 你按下那个键，它告诉你哪个进程收到了。
3. **为什么按下去毫无反应？** —— 区分「根本没到达系统就被吞掉」和「到了，但在持有者看到之前被截胡」。

单文件 `HotkeyHound.exe`，免安装，不用另外下 .NET（Windows 10/11 自带 .NET Framework 4.8）。
MIT 许可。*与 Kimi Code 共同开发。* · **落地页：** <https://conste11ation117.github.io/HotkeyHound/>

## 30 秒上手

1. 从 [Releases](../../releases) 下载 `HotkeyHound.exe`，双击运行。不安装任何东西。
2. **第一次打开会先问界面语言**——默认英文，可选简体中文；之后随时能在「报告与关于」页切换。
   选择保存在 `%LOCALAPPDATA%\HotkeyHound\settings.ini`。
3. 程序停在**扫描总览**页，点「开始扫描」。一两秒完成：引擎 A 试探约 1650 个组合，引擎 D 读取
   已知软件的配置文件。
4. 这台机器上的结果是：**约 220 个组合已被占用**、**54 条配置里声明过**、**真相表 1651 行**。
   你的数字会不一样——这正是要扫描的原因。
5. **报告与关于 → 生成报告**，得到一个自包含的 HTML 文件，可以直接发给别人。

## 「我的快捷键按了没反应」——我在哪种情况里？

按症状找到对应的页，点对应的按钮。每条结论旁边都会印出它的证据。

| 你看到的情况 | 去哪个页面 | 点什么 | 会得到什么 |
|---|---|---|---|
| 快捷键触发错了东西或没反应，但**明显有软件占着它** | **扫描总览** → 真相表 | 开始扫描 | 该组合在「已占用」里，能读到配置的话还会写明是谁声明的 |
| 某个键没反应，想知道**到底谁收到了它** | **按键归属** | 开始监听（安装钩子），按下该键 | 进程名、PID、路径、位数、是否提权 |
| 按键**完全没留下痕迹**，连归属都抓不到 | **钩子检测** | 布防（安装钩子），按下该键，看结论 | 被上层钩子吞掉 / 疑似被截胡 / 不是全局热键 / 正常送达；前提不足时给「无法判定」而不是硬猜 |
| 修饰键像卡住了，或者某些键打出来的字符不对 | **按键监视** | 开始监视（安装钩子），按下该键 | 三层输入（raw input / 低层钩子 / 本窗口）分别有没有看到这个键，外加卡住的修饰键、扫描码重映射、键盘过滤驱动 |
| 「扫描说空闲，但按下去还是有反应」 | **钩子嫌疑** | （随扫描自动填充） | 用钩子实现快捷键的软件清单，每条带明确证据等级，以及它读取的配置文件路径 |

## 每个页面回答什么问题

| 页面 | 回答的问题 | 是否只读 |
|---|---|---|
| **扫描总览** —— 占用扫描 | 哪些组合被占用、谁声明了它们 | 只读，不装钩子 |
| **按键归属** —— 引擎 B | 我刚按下的热键被哪个进程收到了 | 按需装钩子 |
| **钩子检测** —— 引擎 C | 我的键是在到达系统之前被吞了，还是到了之后被截的 | 按需装钩子 |
| **按键监视** —— 输入分层 | raw input、低层钩子、本窗口三层是否都看到这个键；修饰键是否卡住 | 按需装钩子 |
| **配置真相表** —— 引擎 A + D | 声明过什么、实测到什么，按四种状态分组 | 只读，不装钩子 |
| **钩子嫌疑** —— 知识库 + 证据 | 哪些软件会用钩子吃键，我们有多确定 | 只读，不装钩子 |
| **报告与关于** | 导出成一份 HTML；语言、主题、版本 | 只读 |

## 真相表怎么读

每一行是一个组合，处于四种状态之一：

- **有声明且实测被占用** —— 配置和探测都同意，软件确实拿着它。
- **有声明但没注册成功** —— 配置里写了，但探测没人应答：软件没运行，或者它用钩子实现。行里会写明是哪种。
- **被占用但无人认领** —— 有人拿着，但读得到的配置里都没提到。通常是输入法、聊天软件或驱动。
- **空闲** —— 可以放心用；报告会列出不和它冲突的具体候选组合。

在此之上还有一层**钩子嫌疑知识库**：那些快捷键根本不走 `RegisterHotKey` 的软件（PowerToys 键盘
管理器、输入法、QQ/微信、AutoHotkey 脚本、厂商控制中心、投屏工具）。能读配置就读、检查进程是否
在运行，然后给出**明确的证据等级**——实测到 / 从配置读到 / 官方默认 / 仅供参考——并附上产生这条
结论的配置文件路径。**绝不把猜测写成事实。**

## 命令行

```
HotkeyHound.exe                                   # 图形界面
HotkeyHound.exe --scan --report out.html          # 引擎 A + D，生成 HTML 报告
HotkeyHound.exe --listen --seconds 60             # 控制台归属监听（引擎 B）
HotkeyHound.exe --lang en --scan --report en.html # 英文输出
HotkeyHound.exe --elevate --listen                # 提权重启后再监听
HotkeyHound.exe --selftest                        # 自测（会装钩子，见安全模型）
HotkeyHound.exe --monitor --seconds 10            # 按键监视：raw / 钩子 / 窗口三层
HotkeyHound.exe --selftest --no-hooks             # 不碰钩子的自测
HotkeyHound.exe --attribute-all --dry-run         # 规划批量归属，一个键都不按
HotkeyHound.exe --attribute-all --yes             # 逐个按下已占用热键，记录归属
```

## 四个引擎

| 引擎 | 作用 | 是否装钩子 | 是否需要管理员 |
|---|---|---|---|
| **A 占用扫描** | 用 `RegisterHotKey` 逐个试探全部「修饰键 × 按键」组合（约 1650 个），报出哪些已被占用。成功的注册会立刻注销，所以扫描本身没有副作用。 | 否 | 否 |
| **B 按键归属** | 安装全局消息钩子；当热键持有者收到命令时，注入的 DLL 把**是哪个进程收到的**报回来。 | **是** | 建议 |
| **C 钩子窃取检测** | 安装低层键盘钩子，判断你的键是根本没到达系统、到达了但被截胡，还是正常送达。前提缺失（引擎 B 没在监听、扫描没完成）时给「无法判定」，而不是硬猜。 | **是** | 建议 |
| **D 配置聚合** | 解析以明文保存热键设置的软件（PowerToys、Everything、OBS、NVIDIA ShadowPlay 注册表、壁纸引擎、MSI Afterburner），与实测结果做 diff。 | 否 | 否 |

关于 32 位：Windows 只允许钩子注入到与安装它的进程**同位数**的进程，所以 HotkeyHound 会额外拉起一个
很小的 32 位伴随进程来装 32 位钩子；两边把结果报进同一张表，每行都标注位数。

## 安全模型

这个工具会触碰输入处理，所以它的行为被刻意收得很窄：

- **引擎 A / D 从不安装任何东西。** 注册热键后在同一瞬间注销；只读配置文件，**绝不修改配置或注册表**。
- **引擎 B / C 只在用户显式要求时才装钩子。** 界面按钮上直接写着「（安装钩子）」，程序加载时什么都不装。
- **钩子绝不吞键。** 钩子过程只观察、一律放行（`CallNextHookEx`），不改键、不拦键、不延迟。
- **绝不结束、暂停或修改任何其它进程。** 「对照排除」只记录观察结果，请你**自己**退出可疑软件。
- **完全没有网络代码。** 什么都不会离开这台机器。

### 关于注入的 DLL，以及一段必须公开的事故

引擎 B 的机制是安装全局 `WH_GETMESSAGE` 钩子，这意味着 Windows 会把一个原生 DLL **加载进你当前
会话里的每一个进程**。开发过程中，早期版本把钩子过程写成了 **.NET 托管委托**——那个地址只在我们
自己进程里有效，注入到别的进程后就是野指针，后果是**所有 GUI 进程在同一秒集体崩溃**（异常码
`0xc0000409`，故障模块 `unknown`），也就是全机崩。

修复方式（用 `GetProcAddress` 取原生导出地址来装钩子）以及之后的加固——`DllMain` 里什么都不做、
把临界区换成一次性初始化、钩子热路径零分配——**已经在真机上验证**：反复装卸钩子、**崩溃事件 0 次**，
并端到端抓到过一次真实归属（`Win+R → explorer.exe`）。这段事故写进了 CHANGELOG 而不是被悄悄抹掉，
因为使用钩子类工具的人有权知道它的历史。

一次钩子会话结束后，被注入的进程里仍会留着一份 DLL，直到这些进程退出；**重启一次即彻底清除**。
界面里也会提示这一点。

## 已知限制

- **要处理提权进程，必须以管理员身份运行 HotkeyHound**，否则它们的热键查不到归属。
  界面会提示，并提供一键提权重启。
- **钩子型热键对占用扫描不可见**（它们不调用 `RegisterHotKey`）——这正是引擎 B / C 存在的理由，
  报告里始终会印这句提醒。
- **32 位进程能覆盖，但依赖 32 位伴随宿主**：宿主启动失败时那一行会缺失，日志里写明原因。
- 探测是**会话级**的：别的登录会话注册的热键看不到。
- 验证环境为 Windows 11 26100 与 Windows 10 19045；其它版本未测试。

## 从源码构建

构建刻意做到零依赖：开发机上**没有 .NET SDK**，所以工程直接用 Visual Studio 自带的工具链编译。

```
powershell -ExecutionPolicy Bypass -File build.ps1
```

`build.ps1` 先用 MSVC 编译原生 hook DLL（`cl /LD /MT`），再用 Visual Studio 自带的 Roslyn `csc.exe`
编译 C#（`.NET Framework 4.8`、`-langversion:7.3`、`-nostdlib+` 显式引用运行时程序集），最后把 DLL
作为资源内嵌。产物是单文件 `dist\HotkeyHound.exe`。不联网、不用 NuGet。

目录结构：

```
src\Program.cs            入口、命令行解析
src\Core\                 引擎、模型、报告生成、设置
src\Core\Adapters\        各软件的配置读取（引擎 D）
src\Ui\                   WinForms 各页面
src\Hook\HookDll.cpp      原生 hook DLL（引擎 B）
tests\SelfTest.cs         T1–T10，由 --selftest 驱动
docs\                     帮助文档（中/英）
```

## 跟其它工具比

这一行当里目前有四个还活着的工具，回答的是不同的问题。下面这张表**刻意写成诚实的**——别人某处
更强，就写出来。

| | HotkeyScan | Hotkey Screener | Hotkey Detective | **HotkeyHound** |
|---|---|---|---|---|
| 列出已被占用的组合 | 761 | 列出已注册的 | — | **1650** |
| 已注册热键的归属 | 靠"屏幕上发生了什么"推断 | 全局钩子 + 模拟按键 | 全局钩子，你手按 | **全局钩子，你手按——或可选的批量自动按** |
| 被**键盘钩子**吞掉的键 | 只有在按下产生可见变化时才能发现 | 官方承认看不到 | 官方承认看不到 | **专门的检测器 + 配置知识库，带证据等级** |
| 解释"为什么被占" | 读 PowerToys / ShareX / OBS / AHK 配置 | — | — | **读六类软件，并把用到的配置文件路径印出来** |
| 按键监视（卡住的修饰键、重映射、过滤驱动） | 有 | — | — | **有（1.2.0）** |
| 32 位进程 | 仅 64 位 | **32 + 64** | 提供 x86/x64 两个版本 | **x64 + x86（1.3.0 起）** |
| 能拿给别人看的报告 | — | — | — | **自包含 HTML，中英双语** |
| 许可 | MIT | 闭源 | GPL-3.0 | MIT |

实际意味着：**HotkeyScan 是最接近的同侪**——我们正是因为它的按键监视才补上这一块，1.2.0 起已经
对齐，**Hotkey Screener 对已注册热键的归属最直接**，而 **HotkeyHound 是把"按了没反应"的三种原因
分开**的那一个——被注册占用、在到达系统之前被钩子吞掉、或者它根本不是全局快捷键——并且**每条结论
都给出证据**，而不是直接下断言。

还有两条这个领域里谁都无法越过的边界：**钩子型快捷键和应用内快捷键列不出来**，因为 Windows 不把
它们放进任何一张表里。宣称能做到的工具都是在猜；这个工具会把「实测到」「从配置读到」「官方默认」
三种证据分开标注。

更老的选项也有：NirSoft 的 HotKeysList（只列注册项、不给归属，且只列到 Windows 8）、以及 PCHunter /
OpenArk 这类内核级反 rootkit 工具——它们能读 win32k 的热键表，但要加载未签名驱动，在现在开启
Secure Boot / HVCI 的 Windows 上会被拦，而且**依然看不到钩子**。
