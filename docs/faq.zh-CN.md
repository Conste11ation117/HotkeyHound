# 常见问题（FAQ）— HotkeyHound

## 我按的快捷键没反应，怎么查出原因？

四步，从最省事的开始：

1. **这个组合到底有没有被占？** 跑 `HotkeyHound.exe --scan`。引擎 A 用 `RegisterHotKey` 逐一试探约 1650 个组合，报出哪些已被占用；探测成功的注册会在同一瞬间注销，所以扫描没有副作用。
2. **是谁占的？** 报告里的真相表会说明它是否来自某个能读到配置的软件（PowerToys、Everything、OBS、NVIDIA、壁纸引擎、MSI Afterburner），并**打印那个配置文件的路径**。
3. **是不是在到达系统之前就被吃了？** 如果扫描说"空闲"但键还是没反应，多半是键盘钩子。`--attribute-all --dry-run` 会告诉你批量的计划；`--attribute-all --yes` 会逐个按下并记录归属。最有价值的结论是**"按下去了但没人响应"**——这说明有东西把这个键吞了。再用 `--monitor`（或界面里的「按键监视」）判断是哪一层吞的。
4. **是键盘、驱动，还是软件？** 按键监视把同一次按键的三层放在一起看：Raw Input（键有没有离开设备）、低层钩子链、窗口消息层。有 raw 没有 hook → 被上游钩子吃了；连 raw 都没有 → 硬件、固件或键盘过滤驱动根本没发出来。

## 为什么扫描说"空闲"，可这个键明明有反应？

因为那个"有反应"根本没注册热键。PowerToys 键盘管理器、输入法、AutoHotkey、部分厂商工具用的是**低层键盘钩子**：按键在到达系统热键分发之前就被处理掉了，`RegisterHotKey` 没有可冲突的对象。这是这类困惑最常见的来源，也正是 HotkeyHound 除了扫描之外还要做钩子检测与配置知识库的原因。

## Windows 自己为什么查不到热键是谁注册的？

系统内部当然知道——热键表在 win32k 里——但没有公开 API 能读。`RegisterHotKey` 没有"回读持有者"的对应函数，公开可见的信号只有失败码 `ERROR_HOTKEY_ALREADY_REGISTERED`（1409）。其余一切都要靠推断：探测占用、观察投递、或者读占用方自己的配置。

## 那别的工具是怎么做的？

- **Hotkey Screener**：装全局消息钩子，**模拟按下**那个热键，看谁响应。有效，但检测过程真的会触发那些功能。
- **Hotkey Detective**：把钩子装进每个进程，等你手动按键。
- **内核级反 rootkit 工具**（PCHunter、OpenArk）：直接读 win32k 的热键表，但要加载未签名驱动，在开启 Secure Boot / HVCI 的现代 Windows 上会被拦，而且**依然看不到钩子**。
- **HotkeyHound**：全程用户态，并且比上面几个多一件事——读嫌疑软件的配置，因此能解释"为什么被占"，每条结论还带证据等级。

## 它会记录我的按键吗？会联网吗？

没有一行网络代码：不上传、无遥测、无统计、不检查更新。钩子过程只观察并一律放行，**不保存你输入的内容**。按键监视只在你显式开始监视时、只在内存里记录你按下的那些键（以及你自己导出的内容），不写盘。

## 需要管理员权限吗？

引擎 A、引擎 D 和报告：不需要。要给**提权进程**（例如以管理员运行的 PowerToys）查归属才需要提权，因为 Windows 不允许低完整性进程往高完整性进程注入钩子（UIPI）。界面会检测这种情况并提供"以管理员身份重启"按钮，命令行用 `--elevate`。

## 它能覆盖哪些进程？

- **64 位进程**：能（在完整性允许的范围内）。
- **32 位进程**：1.3.0 起支持。Windows 只允许钩子注入到与安装者同位数的进程，所以 HotkeyHound 会额外拉起一个很小的 32 位伴随进程来装 32 位钩子；两边把结果报进同一张表，每行都会标注位数（x64 / x86）。
- **其它登录会话里的进程**：看不到——热键是会话级的。

## 它会往每个进程注入 DLL，安全吗？

注入的 DLL 尽量什么都不做：只导出一个钩子过程，把消息和 `WM_HOTKEY` 比一下，向控制器投一条消息，然后照常 `CallNextHookEx` 放行。`DllMain` 里除了 `DisableThreadLibraryCalls` 不写任何东西；共享内存握手只初始化一次。钩子**只在你按下明确写着"安装钩子"的按钮时**才装。

这个项目也公开自己的历史：早期开发版把**托管委托**当成了原生钩子过程，导致每个 GUI 进程同时崩溃。修复、加固以及防止复发的硬规矩都写在 `CHANGELOG.md` 与 `AGENTS.md` 里。

## 怎么彻底清理？

关掉程序、删掉 exe 就完事——它是单文件、没有安装器。可能留下两样东西：`%LOCALAPPDATA%\HotkeyHound\`（释放的钩子 DLL 与设置），以及会话期间被注入过的进程里仍加载着的那份钩子 DLL。两者重启后都会消失，那个文件夹之后可以手动删除。

## 为什么不用内核驱动？驱动不是能枚举一切吗？

驱动能读热键表，但**看不到钩子**——而钩子恰恰是最难查、最常见的一类。为它付出未签名驱动（被 Secure Boot 与 HVCI 拦、被反作弊与杀软误判）的代价，却仍然漏掉主要场景，不划算。读配置是一条朴素、可审计的替代路线，而且能直接告诉用户该去改哪个文件。

## 报告里写"已知默认"是什么意思？

意思是这条热键来自软件官方文档的默认值，因为在这台机器上读不到它的配置（加密、二进制、或被运行中的进程锁住）。它会如实标注，而不是被当成实测事实。证据共四个等级：**已确认 / 高度怀疑 / 已知默认 / 仅供参考**。
