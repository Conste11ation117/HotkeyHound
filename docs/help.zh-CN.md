# HotkeyHound 帮助（简体中文）

HotkeyHound 是一个 Windows 全局快捷键冲突排查工具。它帮你看清楚：**哪些热键被占用了、被谁占用了、
为什么你按下去的键没有反应、以及哪些键是空闲的可放心使用。**

它只读取和探测，不修改任何配置、不写注册表、不结束任何进程。

---

## 1. 这个工具解决什么问题

日常里最烦的几种情况，HotkeyHound 都有对应手段：

- 想给某个软件设一个全局热键，却提示「快捷键已被占用」，但不知道被谁占了。
- 某个键按下去毫无反应，说不清是被别的软件抢了，还是被某个钩子吞了。
- 换电脑 / 装了新软件后，一堆原来的快捷键行为变了，想排查是哪一个软件造成的。
- 想知道某一组键（例如 `Ctrl+Alt+F13`）到底是不是空着，能不能拿来用。

它由四个引擎组成，分别回答上面不同的问题。

---

## 2. 四个引擎

### 引擎 A —— 占用扫描（只读，不需要管理员）

**做什么**：对每一种「修饰键组合 × 按键」（约 1650 个组合）调用 Win32 `RegisterHotKey` 试探：
成功就立刻 `UnregisterHotKey` 注销，记为**空闲**；失败且错误码为 1409
（`ERROR_HOTKEY_ALREADY_REGISTERED`）记为**已占用**。

**怎么用**：图形界面「扫描总览」页点「开始扫描」，或命令行

```
HotkeyHound.exe --scan --report 我的报告.html
```

**风险**：几乎为零。扫描过程不改设置、不写注册表，注册动作在同一瞬间被撤销。

### 引擎 B —— 按键归属（需要安装钩子；建议管理员）

**做什么**：装一个全局消息钩子（`WH_GETMESSAGE`，由一个原生 DLL 实现），拦截
`WM_HOTKEY` 消息。当你按下某个全局热键时，持有它的进程会收到这条消息，钩子顺手把
「持有者进程 PID + 组合键」报回来，于是你就知道**这个热键究竟是谁的**。

**怎么用**：图形界面「按键归属」页点「开始监听」，然后按下想排查的热键；或命令行

```
HotkeyHound.exe --listen --seconds 30
```

**32 位进程**：Windows 只允许钩子注入到与安装者**同位数**的进程。本程序是 64 位，所以开始监听时会
自动再拉起一个很小的 32 位宿主（`HotkeyHound.Helper32.exe`）来装 32 位钩子；两条链路的记录进入同一张表，
每条都标注目标进程的位数（x64 / x86）。32 位宿主启动失败只影响 32 位覆盖，原因会写进日志，64 位路径不受影响。

**风险**：这一项会安装全局钩子，且会把原生 DLL 注入到当前会话的每个进程。因此：

- **只有你显式点「开始监听」时才安装**，点「停止监听」立刻卸载；
- 程序加载界面时**不会**安装任何钩子；
- 请尽量以管理员身份运行，否则看不到提权进程（例如以管理员运行的 PowerToys）。

### 引擎 C —— 钩子窃取检测（需要安装钩子）

**做什么**：装一个低层键盘钩子 `WH_KEYBOARD_LL`，观察按键是否到达系统。结合引擎 A 的占用表与
引擎 B 的归属报告，给出四分支结论：

| 结论 | 含义 |
|---|---|
| 正常送达 | 按键到达系统，并且收到了明确的归属报告 |
| 疑似被钩子截胡 | 按键到了系统，但持有者没收到命令——被某个钩子拦了 |
| 被上层钩子吞掉 | 本程序的钩子根本没看到这个键，说明更上层有钩子把它吞了 |
| 不是全局热键 | 看到了，但引擎 A 里它不是已占用，说明只是当前窗口自己处理的键 |

**怎么用**：图形界面「钩子检测」页，填好组合键点「布防（安装钩子）」（**此刻才装钩子**），
立即按下该键，看结论。判定为「被吞掉」时，用右侧「对照排除」工作流逐条记录、人工退出可疑软件再对比。

**风险**：同样会安装钩子。本页**只观察、不吞键、不改键，也绝不结束或暂停任何进程**。

### 引擎 D —— 配置聚合（只读，不需要管理员）

**做什么**：解析已知软件的配置文件（PowerToys、Everything、OBS、NVIDIA ShadowPlay、
Wallpaper Engine、MSI Afterburner 等）里的热键声明，和引擎 A 的实测结果做 diff，产出「真相表」。

**怎么用**：跟着 `--scan` / 「开始扫描」一起自动运行，结果在「配置真相表」页和报告里。

**风险**：无。所有读取都是只读，损坏或缺失的配置文件会被跳过。

## 3. 为什么「扫描说空闲」也可能被占用

这是最容易误解的一点。引擎 A 只能看到通过 `RegisterHotKey` 注册的热键；有一大类热键**不经过它**：

- **键盘钩子型热键看不到。** PowerToys 键盘管理器、AutoHotkey、输入法、部分游戏工具用底层键盘钩子
  实现热键。它们不调用 `RegisterHotKey`，所以引擎 A 会把键位报成「空闲」——但实际按下后会被它们抢先处理。
- **只有当前会话可见。** `RegisterHotKey` 是会话级/窗口站级的，别的登录会话注册的热键这里探测不到。
- **「注册失败」不等于「软件占用」。** 少数组合会返回 1409 之外的错误码（系统保留或特殊限制），
  报告里会把错误码一并列出。

结论：引擎 A 说「空闲」只是「没有别人通过 RegisterHotKey 占了它」。要确认「按下去到底有没有人响应」，
请用引擎 B 监听、用引擎 C 判断是否被钩子吞掉。

## 4. 用引擎 B 找出「按了没反应的键」

假设某个键按下去没反应，你想知道是被谁处理了：

1. 打开「按键归属」页（或 `--listen`），点「开始监听」。
2. 按下那个键，观察是否出现归属记录。
3. 分两种情形：
   - **出现记录**：记录里写明是哪个进程持有了它。就是那个软件把它抢走了。
   - **没有记录**：说明它要么不是全局热键（只是当前窗口自己处理的键），要么被更上层的钩子吞掉了。
     这时用引擎 C（「钩子检测」页）进一步判断。

小技巧：把 `--listen` 和引擎 C 的对照排除工作流配合使用——先记录「现在」的结论，退出一个可疑软件，
再测一次，对比两次结果就能定位到责任软件。

## 5. 自动归属：把「已占用但不知道主人」批量问出来

引擎 A 能告诉你哪些组合被占用，却不会告诉你是谁。自动归属把两件事接起来：对每个已占用组合
**模拟按下**，再用引擎 B 的归属报告问出主人。

命令行（默认是 dry-run，只打印「将按哪些、跳过哪些、原因」，**一次都不真按**）：

```
HotkeyHound.exe --attribute-all --dry-run
HotkeyHound.exe --attribute-all --yes --report 归属报告.html --max 30
```

- 只有同时给 `--yes` 才会真的按键；不给就永远只做 dry-run。
- 黑名单**硬编码、不可放宽**：任何含 `Win` 的组合、`Alt+F4`、`Alt+Tab`、`Alt+Esc`、`Alt+Space`、
  `Ctrl+Esc`、`Ctrl+Alt+Del`、`Ctrl+Shift+Esc`、`Ctrl+Alt+Tab`。这些键按下去会切窗口、关程序或触发系统界面。
- 每次按键间隔至少 400 毫秒，归属等待 1.2 秒，默认最多 30 个（`--max` 可调）；**按 Esc 立即中止**。
- 结果分三类：**已归属**（拿到了归属进程）、**无响应**（按下去了但 1.2 秒内持有者没收到，高度怀疑被钩子吞掉）、
  **跳过**（黑名单/超过上限/中止/输入失败）。中止、超时与跳过都会如实统计并写进报告。

**风险（务必先读）**：模拟按下会真的触发这些热键的功能——可能开始录屏/录音、打开面板、切换输入法、
弹出窗口，甚至启动程序。图形界面里点「自动归属已占用组合」会先弹出风险确认框，确认后才执行；
执行中显示进度，可随时按 Esc 或点「中止」。如果不确定，就先用 `--dry-run` 看计划。

## 6. 钩子嫌疑怎么读

第 6 个页签「钩子嫌疑」和报告里的 `#hooksuspects` 区块，来自一份只读的钩子型热键知识库
（构建时内嵌的 `data/hook-catalog.json`；你也可以把同名文件放到
`%LOCALAPPDATA%\HotkeyHound\catalog.json` 覆盖或追加条目）。它只做三件事：读该软件的配置、
看该进程是否在运行、对照引擎 A 的实测占用。

证据等级必须按下面的定义读，工具不会把猜测写成事实：

| 等级 | 含义 |
|---|---|
| 已确认 | 配置里明确写了这个组合，且软件正在运行 |
| 高度怀疑 | 只有一侧证据：配置写了但软件没运行，或配置读不出来但进程在跑且已知它有钩子热键 |
| 已知默认 | 该软件的出厂默认快捷键，本机没能读到配置 |
| 仅供参考 | 该软件确实用钩子，但具体键位无法确定 |

用法：先扫描；打开「钩子嫌疑」页，按证据等级筛选；双击一行或点「打开配置所在目录」跳到它的
配置位置。页面加载**不安装任何钩子**。

重要：**「不在清单里」不等于「没有钩子」**。知识库只覆盖已知软件；要确认某个按键是否真的被吞掉，
仍然应该用引擎 C（「钩子检测」页）。如果报告建议区出现「按下去没反应？很可能被 X 的钩子吞了」，
说明该组合在引擎 A 里是空闲的、而 X 有对应的钩子嫌疑——去 X 的设置里改掉它。

## 7. 按键监视（Key monitor）怎么用、结论怎么读

扫描和归属回答不了「这个键到底在哪一层丢的」。「按键监视」页同时观察三层，并给出结论：

1. **Raw Input（设备层）**：键盘是否把按键送到了 Windows；
2. **WH_KEYBOARD_LL（钩子链）**：按键是否到达本程序的低层键盘钩子；
3. **窗口消息**：本程序窗口是否收到 `WM_KEYDOWN` / `WM_KEYUP`（只有本窗口聚焦时才可能）。

用法：打开「按键监视」→ 点「开始监视（安装键盘钩子）」→ 按下有问题的键 → 看「判定结果」卡片。
按钮文案写明会安装钩子；点「停止监视」立刻 `UnhookWindowsHookEx` 并注销 Raw Input。**页面加载时不会安装任何钩子**。

| 判定 | 含义 | 建议的下一步 |
|---|---|---|
| 设备层就没上来 | Raw Input 根本没见过这个键 | 换键盘/接口复测；看下方键盘类驱动清单（只读，不判定、不卸载） |
| 钩子链之前被吞 | Raw Input 看到了，低层钩子没看到 | 更上游的钩子/驱动（输入法、厂商驱动、宏、远控）在设备层之后、钩子链之前拦截 |
| 钩子之后被截胡 | Raw + 钩子都有，是全局热键，但引擎 B 没报出持有者 | 先到「按键归属」页开始监听再复测；仍无归属就用「钩子检测」的对照排除逐个退出可疑软件 |
| 已送达 | 三层都有；或全局热键拿到了归属 | 输入链路正常，问题在接收按键的软件本身 |
| 无法确定 | 是全局热键，但归属引擎没有运行 | 这不是「没问题」，是证据不足；开「按键归属」后重测 |

**卡住的修饰键**：逐个查左右 Ctrl/Alt/Shift/Win 的 `GetAsyncKeyState`，与钩子看到的状态对照。
「系统说按着、钩子没看到」也可能只是开始监视前就按住了这个键——松开再按一次即可确认。

**重映射与驱动（只读）**：`HKLM\SYSTEM\CurrentControlSet\Control\Keyboard Layout\Scancode Map`
会解析成「按下 X → 系统产生 Y」的列表；`HKLM\SYSTEM\CurrentControlSet\Services` 下符合
`Type=1`、`Start≠4`、组名/驱动名像键盘类的服务只**列出**供参考。工具不判定、不停止、不卸载任何驱动。
## 8. 权限与完整性说明

- **管理员（UAC）**：非管理员运行时，看不到「以管理员身份运行的进程」的热键归属（例如 PowerToys）。
  界面顶部提示条和「扫描总览」页都有「以管理员身份重启」按钮；命令行可用 `--elevate` 提权重启
  （会保留原命令行参数）。用户在 UAC 里点「否」时程序会识别为「已取消」并正常返回，不会报错崩溃。
- **低完整性（Low IL）**：如果 exe 位于带 `Mandatory Label\Low` 标签的目录（例如某些同步盘工作区），
  进程会以低完整性运行。后果：写 `%TEMP%`、`%LOCALAPPDATA%` 会被拒绝；**UIPI 会拦住钩子注入**，
  引擎 B/C 基本失效。**请把 exe 复制到普通目录（如 `C:\Tools\`）后再运行。**
- **UIPI（用户界面特权隔离）**：低完整性或非提权进程无法向更高完整性进程注入钩子，这是 Windows 的
  安全机制，不是本工具的 bug。

## 9. 已知限制

- **32 位覆盖依赖额外的 32 位宿主**：Windows 不允许 64 位钩子注入 32 位进程，所以 32 位进程由开始监听时
  自动拉起的 32 位宿主覆盖；若它被安全软件拦截、或被释放/启动失败，这部分归属会缺失，原因写在本程序日志里。
  归属列表和报告里每行都标注目标进程的位数（x64 / x86）。
- **钩子型热键不走 WM_HOTKEY**：用键盘钩子实现的热键（键盘管理器、输入法、AutoHotkey）不会出现在
  引擎 A 的占用表里，也不会触发引擎 B 的归属报告。
- **只覆盖当前会话**：别的登录会话的热键看不到。
- **部分配置编码未验证**：MSI Afterburner、Everything 的热键编码格式需要人工核对。
- **引擎 B/C 需要装钩子**：这是设计使然，且只在显式操作时发生。

## 10. 常见问题排查

**Q：扫描不到任何占用 / 数字明显偏小？**
A：确认没有同时运行另一个会大量注册热键的程序；换到普通目录重跑（低完整性会影响写入与探测）。

**Q：「开始监听」报错或一个进程都看不到？**
A：多半是低完整性（把 exe 复制到普通目录）或非管理员（用「以管理员身份重启」/ `--elevate`）。

**Q：报告写不进去 / 提示拒绝访问？**
A：把输出路径改到可写目录（例如程序所在目录）。低完整性进程写不了 `%TEMP%`、`%LOCALAPPDATA%`。

**Q：某个键在引擎 A 里是空闲的，但按下去还是没反应？**
A：它很可能被钩子型热键占用了。用引擎 B 监听、引擎 C 判断。

**Q：怎么把界面切成英文？**
A：命令行加 `--lang en`，或在「报告与关于」页 / 帮助窗口里切换语言（切换后重启程序生效）。

## 11. 卸载 / 清理

HotkeyHound 是绿色单文件程序，**没有安装程序、不写注册表**：

- 直接删除 `HotkeyHound.exe` 即可。
- 程序会在 `%LOCALAPPDATA%\HotkeyHound\`（或 exe 同目录）下释放引擎 B 用的原生 DLL
  （`HotkeyHound.Hook.dll`）、32 位链路的两个产物（`hooks\x86\HotkeyHound.Hook32.dll` 与
  `HotkeyHound.Helper32.exe`）以及 `settings.ini`。删除该目录即可。
- 引擎 B 的 DLL 会被注入到当前会话的进程里；这些注入**在进程重启后自然消失**，
  **重启电脑可彻底清除**。停止监听时本程序也会调用 `UnhookWindowsHookEx` 卸载钩子。
