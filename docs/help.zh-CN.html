HotkeyHound 帮助

简易使用：首次启动会先让你选择界面语言（之后可在“报告与关于”改）；然后点“扫描总览 → 开始扫描”看哪些组合被占用；想知道归属用“按键归属”；按下没反应用“钩子检测”。

只读取与探测，不修改配置、不写注册表、不结束任何进程。

1. 这个工具解决什么问题

  • 想设一个全局热键，却提示「已被占用」，但不知道被谁占了。
  • 某个键按下去毫无反应，说不清是被别的软件抢了，还是被某个钩子吞了。
  • 换电脑 / 装了新软件后一批快捷键行为变了，想找出是哪个软件造成的。
  • 想知道某一组键（例如 Ctrl+Alt+F13）到底是不是空着。

2. 四个引擎

引擎 A —— 占用扫描（只读，不需要管理员）

对每一种「修饰键组合 × 按键」（约 1650 个）调用 RegisterHotKey 试探：成功立刻 UnregisterHotKey，记为空闲；失败且错误码为 1409（ERROR_HOTKEY_ALREADY_REGISTERED） 记为已占用。用法：界面「扫描总览」点「开始扫描」，或 HotkeyHound.exe --scan --report 报告.html。 风险：几乎为零——不改设置、不写注册表，注册动作在同一瞬间被撤销。

引擎 B —— 按键归属（需要安装钩子；建议管理员）

装一个全局消息钩子（WH_GETMESSAGE，由原生 DLL 实现）拦截 WM_HOTKEY。 按下全局热键时，持有它的进程会收到消息，钩子把「持有者 PID + 组合键」报回来，于是你就知道这个热键是谁的。 用法：界面「按键归属」点「开始监听」后按热键，或 HotkeyHound.exe --listen --seconds 30。

32 位进程：Windows 只允许钩子注入与安装者同位数的进程；本程序是 64 位，所以开始监听时会自动再拉起 一个很小的 32 位宿主（HotkeyHound.Helper32.exe）装 32 位钩子。两条链路的记录进入同一张表， 每行都标注目标进程的位数（x64 / x86）；32 位宿主启动失败只影响 32 位覆盖，原因写进日志，64 位路径不受影响。

风险：这一项会安装全局钩子并把原生 DLL 注入当前会话的每个进程。 只有你显式点「开始监听」时才安装，点「停止监听」立刻卸载；加载界面时不会安装任何钩子。 请尽量以管理员运行，否则看不到提权进程（如以管理员运行的 PowerToys）。

引擎 C —— 钩子窃取检测（需要安装钩子）

装一个低层键盘钩子 WH_KEYBOARD_LL 观察按键是否到达系统，结合引擎 A 占用表与引擎 B 归属报告 给出结论。前提不满足时诚实报告「无法判定」，绝不硬猜：

结论含义
正常送达按键到达系统，并收到了明确的归属报告
疑似被钩子截胡按键到了系统、引擎 B 也在监听，但持有者没收到命令——被某个钩子拦了
被上层钩子吞掉本程序的钩子根本没看到这个键，说明更上层有钩子把它吞了
不是全局热键看到了，但引擎 A 里它不是已占用，说明只是当前窗口自己处理的键
无法判定（条件不足）引擎 B 未在监听，或引擎 A 还没扫描——证据不足，不下结论

用法：界面「钩子检测」页填好组合键点「布防（安装钩子）」（此刻才装钩子）。若引擎 B 尚未启动， 会弹一次确认框，同意后一并启动（没有引擎 B 就没法证明「截胡」）。随后立即按下该键看结论。 本页只观察、不吞键、不改键，也绝不结束或暂停任何进程。

引擎 D —— 配置聚合（只读，不需要管理员）

解析已知软件（PowerToys、Everything、OBS、NVIDIA ShadowPlay、Wallpaper Engine、MSI Afterburner 等）配置里的 热键声明，与引擎 A 实测结果做 diff，产出「真相表」。跟 --scan / 「开始扫描」自动运行。无风险，只读。

3. 为什么「扫描说空闲」也可能被占用

  • 键盘钩子型热键看不到。PowerToys 键盘管理器、AutoHotkey、输入法、部分游戏工具用底层键盘钩子实现热键， 不经过 RegisterHotKey，引擎 A 会报成「空闲」，但按下后会被它们抢先处理。
  • 只有当前会话可见。RegisterHotKey 是会话级/窗口站级的，别的登录会话注册的热键探测不到。
  • 「注册失败」不等于「软件占用」。少数组合会返回 1409 之外的错误码（系统保留或特殊限制），报告里会列出错误码。

所以引擎 A 说「空闲」只是「没有别人通过 RegisterHotKey 占了它」。要确认按下去到底有没有人响应，请用引擎 B、引擎 C。

4. 用引擎 B 找出「按了没反应的键」

  1. 打开「按键归属」页（或 --listen），点「开始监听」。
  2. 按下那个键，观察是否出现归属记录。
  3. 出现记录：写明是哪个进程持有了它——就是那个软件抢走了。
    没有记录：它要么不是全局热键，要么被更上层的钩子吞了；用引擎 C 进一步判断。

技巧：配合引擎 C 的对照排除工作流——先记录「现在」的结论，退出一个可疑软件，再测一次并对比。

5. 自动归属：把「已占用但不知道主人」批量问出来

引擎 A 能告诉你哪些组合被占用，却不会告诉你是谁。自动归属把两件事接起来：对每个已占用组合 模拟按下，再用引擎 B 的归属报告问出主人。

HotkeyHound.exe --attribute-all --dry-run
HotkeyHound.exe --attribute-all --yes --report 归属报告.html --max 30
  • 默认是 dry-run：只打印「将按哪些、跳过哪些、原因」，一次都不真按。只有加 --yes 才会真的按键。
  • 黑名单硬编码、不可放宽：任何含 Win 的组合、Alt+F4、Alt+Tab、 Alt+Esc、Alt+Space、Ctrl+Esc、Ctrl+Alt+Del、 Ctrl+Shift+Esc、Ctrl+Alt+Tab。这些键按下去会切窗口、关程序或触发系统界面。
  • 每次按键间隔至少 400 毫秒，归属等待 1.2 秒，默认最多 30 个（--max），按 Esc 立即中止。
  • 结果分三类：已归属、无响应（按下去了但持有者没收到，高度怀疑被钩子吞掉）、 跳过（黑名单/超过上限/中止/输入失败）。中止、超时与跳过都会如实统计。

风险：模拟按下会真的触发这些热键的功能——可能开始录屏/录音、打开面板、切换输入法、弹出窗口， 甚至启动程序。图形界面里点「自动归属已占用组合」会先弹风险确认框，确认后才执行；执行中显示进度， 可随时按 Esc 或点「中止」。不确定就先用 --dry-run 看计划。

6. 钩子嫌疑怎么读

第 6 个页签「钩子嫌疑」和报告里的 #hooksuspects 区块，来自一份只读的钩子型热键知识库 （构建时内嵌的 data/hook-catalog.json；你也可以把同名文件放到 %LOCALAPPDATA%\HotkeyHound\catalog.json 覆盖或追加条目）。它只做三件事：读该软件的配置、 看该进程是否在运行、对照引擎 A 的实测占用。

证据等级含义
已确认配置里明确写了这个组合，且软件正在运行
高度怀疑只有一侧证据：配置写了但软件没运行，或配置读不出来但进程在跑且已知它有钩子热键
已知默认该软件的出厂默认快捷键，本机没能读到配置
仅供参考该软件确实用钩子，但具体键位无法确定

用法：先扫描；打开「钩子嫌疑」页，按证据等级筛选；双击一行或点「打开配置所在目录」跳到它的配置位置。 页面加载不安装任何钩子。

「不在清单里」不等于「没有钩子」。知识库只覆盖已知软件；要确认某个按键是否真的被吞掉，仍然应该用 引擎 C（「钩子检测」页）。如果报告建议区出现「按下去没反应？很可能被 X 的钩子吞了」，说明该组合在引擎 A 里 是空闲的、而 X 有对应的钩子嫌疑——去 X 的设置里改掉它。

7. 按键监视怎么用、结论怎么读

扫描和归属回答不了「这个键到底在哪一层丢的」。「按键监视」页同时观察三层：

  1. Raw Input（设备层）：键盘是否把按键送到了 Windows；
  2. WH_KEYBOARD_LL（钩子链）：按键是否到达本程序的低层键盘钩子；
  3. 窗口消息：本程序窗口是否收到 WM_KEYDOWN/WM_KEYUP（只有本窗口聚焦时才可能）。

用法：打开「按键监视」→ 点「开始监视（安装键盘钩子）」→ 按下有问题的键 → 看「判定结果」卡片。 按钮文案写明会安装钩子；点「停止监视」立刻 UnhookWindowsHookEx 并注销 Raw Input。 页面加载时不会安装任何钩子。

判定含义建议的下一步
设备层就没上来Raw Input 根本没见过这个键换键盘/接口复测；看下方键盘类驱动清单（只读，不判定、不卸载）
钩子链之前被吞Raw Input 看到了，低层钩子没看到更上游的钩子/驱动（输入法、厂商驱动、宏、远控）在设备层之后、钩子链之前拦截
钩子之后被截胡Raw + 钩子都有，是全局热键，但引擎 B 没报出持有者先到「按键归属」页开始监听再复测；仍无归属就用「钩子检测」的对照排除逐个退出可疑软件
已送达三层都有；或全局热键拿到了归属输入链路正常，问题在接收按键的软件本身
无法确定是全局热键，但归属引擎没有运行这不是「没问题」，是证据不足；开「按键归属」后重测

卡住的修饰键：逐个查左右 Ctrl/Alt/Shift/Win 的 GetAsyncKeyState，与钩子看到的状态对照。 「系统说按着、钩子没看到」也可能只是开始监视前就按住了这个键——松开再按一次即可确认。

重映射与驱动（只读）：Scancode Map 会解析成「按下 X → 系统产生 Y」的列表； HKLM\SYSTEM\CurrentControlSet\Services 下符合 Type=1、Start≠4、 组名/驱动名像键盘类的服务只列出供参考。工具不判定、不停止、不卸载任何驱动。

8. 权限与完整性

  • 管理员（UAC）：非管理员看不到「以管理员运行的进程」的热键归属。界面顶部提示条与「扫描总览」页都有 「以管理员身份重启」按钮；命令行用 --elevate 提权重启（保留原命令行参数）。 用户在 UAC 里点「否」时程序识别为「已取消」并正常返回，不会报错崩溃。
  • 低完整性（Low IL）：exe 若位于带 Mandatory Label\Low 标签的目录，进程会以低完整性运行—— 写 %TEMP%/%LOCALAPPDATA% 被拒，UIPI 拦住钩子注入，引擎 B/C 基本失效。 请把 exe 复制到普通目录（如 C:\Tools\）后再运行。
  • UIPI：低完整性或非提权进程无法向更高完整性进程注入钩子，这是 Windows 的安全机制，不是本工具的 bug。

9. 已知限制

  • 32 位覆盖依赖额外的 32 位宿主：Windows 不允许 64 位钩子注入 32 位进程，所以 32 位进程由开始监听时 自动拉起的 32 位宿主覆盖；若它被安全软件拦截或释放/启动失败，这部分归属会缺失（原因写在日志里）。 归属列表和报告里每行都标注目标进程的位数（x64 / x86）。
  • 钩子型热键不走 WM_HOTKEY：这类热键不会出现在引擎 A 占用表，也不触发引擎 B 归属报告。
  • 只覆盖当前会话：别的登录会话的热键看不到。
  • 部分配置编码未验证：MSI Afterburner、Everything 的编码需人工核对。
  • 引擎 B/C 需要装钩子：设计使然，且只在显式操作时发生。

10. 常见问题排查

  • 扫描不到占用 / 数字偏小？确认没有别的程序在大量注册热键；换到普通目录重跑。
  • 「开始监听」报错或看不到进程？多半是低完整性（复制到普通目录）或非管理员（提权重启）。
  • 报告写不进去？把输出路径改到可写目录；低完整性进程写不了 %TEMP%、%LOCALAPPDATA%。
  • 引擎 A 说空闲但按下去没反应？很可能被钩子型热键占用了，用引擎 B、引擎 C 排查。
  • 怎么切成英文？命令行加 --lang en，或在本帮助窗口 / 「报告与关于」页切换（重启生效）。

11. 卸载 / 清理

  • 绿色单文件程序：直接删除 HotkeyHound.exe 即可，无安装程序、不写注册表。
  • 程序会在 %LOCALAPPDATA%\HotkeyHound\（或 exe 同目录）释放引擎 B 用的原生 DLL （HotkeyHound.Hook.dll）、32 位链路的两个产物（hooks\x86\HotkeyHound.Hook32.dll 与 HotkeyHound.Helper32.exe）以及 settings.ini，删除该目录即可。
  • 引擎 B 的 DLL 会被注入当前会话的进程；这些注入在进程重启后自然消失，重启电脑可彻底清除。 停止监听时本程序也会调用 UnhookWindowsHookEx 卸载钩子。
